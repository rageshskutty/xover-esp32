# Architecture and constraints

**Status:** decision blueprint. Repository facts are tagged **Fact**; recommendations are **Decision**; unmeasured or owner-controlled items are **Open**. This document does not authorize hardware assumptions.

## System boundary and data flow
**Fact:** v1 is 48 kHz, stereo input, six of eight 32-bit TDM slots to three PCM5122 DACs, DSP on S3 core 1, control/network/configuration on core 0. Existing target build is ESP-IDF style; host DSP/validation is independently built by CMake. Do not add a framework unless the approved audio-source compatibility spike requires it.

**Proposed flow:** bounded source callback → fixed-capacity SPSC PCM ring (core 0 producer, core 1 consumer) → DSP task → 6-channel interleaved frames in 8-slot TDM block → ESP-IDF I2S channel write/DMA → DACs. Control plane: authenticated/bounded HTTP upload → core-0 parse/schema/graph/protection validation → allocate and build inactive graph in internal SRAM → ramp down → atomic pointer swap at block boundary → ramp up → persist active configuration using A/B config slots. Never parse, allocate, log, design filters, or wait for network from DSP task.

**Ownership:** DSP task exclusively owns active graph and all live per-node filter state. Builder owns inactive candidate until publication. Retire prior graph only after DSP task acknowledges that it can no longer reference it (generation/acknowledgment); pointer swap alone is insufficient to free memory safely. Audio input ring is SPSC and fixed capacity; define overflow/underflow counters and fail-safe mute behavior before implementation.

## DSP graph and processing
- Reuse version-1 DAG, bounded 64 nodes, 96 SOS-section cap (current cap is a planned value pending T09 measurement), node schemas, compiler and validators. Input nodes bind channel 0/1; each node has one predecessor except mix (one edge per gain); fanout is allowed; output slots unique.
- Each output path is an ordered cascade of existing block types. Recommended conventional chain: input correction PEQ/shelf when correction is common to both bands → crossover split → band-specific PEQ/shelf → gain/delay/polarity → output. Sub path uses explicit mix, low-pass, output. This is a graph recipe, not a new algorithm. Do not silently auto-invert LR2/LR6; current docs require explicit polarity. Do not assume room measurements or target curve.
- Reuse current bilinear/prewarped Butterworth and LR definitions, RBJ PEQ/shelf/notch/allpass, DF2T float32 processing, double design on core 0 and hi/lo denominator compensation. Bessel stays E_UNSUPPORTED. Preserve exact tested response/golden vectors and config v1.
- **Open design conflict:** proposed crossover+room-correction ordering depends on whether correction is system-wide or per-driver. Default graph supports either through node placement; task cards must not prescribe correction coefficients or targets before measurement requirements exist.
- Runtime update policy: versioned immutable graph, no in-place coefficient/state writes. Initial behavior is mute-ramp-swap (default from PLAN D9); crossfade is deferred until CPU/state budget and owner approval. Gain ramps obey S7 (>=5 ms down, >=20 ms up, no step above -60 dBFS).

## Firmware modules and dependency direction
`main → control/config service → dspgraph → dspblocks`; `main → audiosrc`; `main → tdmout → IDF I2S`; `main → pcm5122` for DAC setup/mute control. No DSP dependency on web, audio decoder, NVS, or hardware driver. `dspgraph` may depend on `dspblocks` and cJSON only. `tdmout` owns slot packing and I2S write; `audiosrc` owns ring and input format conversion; a top-level audio runtime owns task lifecycle, state transitions and safe swap coordination. No circular component dependencies.

## Real-time and resource policy
- Fixed blocks currently documented as 64 frames (1.333 ms at 48 kHz), but this exceeds the existing 1.00 ms maximum gate. **Resolve before accepting T09:** either shorten block (e.g. 32 frames = 0.667 ms, still leaves insufficient margin under 0.60 ms p99.9) or redefine the acceptance budget with measured DMA behavior and owner approval. Do not claim 64-frame compliance.
- For `S` active SOS sections and `C=6) outputs at `fs=48,000`, baseline DF2T workload is roughly 5 multiplies + 4 adds per section per output sample (architecture estimate, not measured); upper rough count = `S × C × 48,000 × 9` scalar arithmetic operations/s, excluding graph copies/mix/conversion. At 96 sections and six channels this is ~249 million scalar ops/s; however section cap counts graph sections, not exact per-output path multiplicity, so worst-case graph execution must be bounded from path expansion before feasibility claim. Use measured ESP32 cycle counts and worst-case graph, not this estimate, to set cap.
- Internal SRAM only for coefficients, states, graph nodes, DMA buffers and ring (AGENTS R3); allocate once outside RT path. PSRAM disabled unless exact module confirmed and never used for active filter state. Double precision only on core 0. Clamp/saturate at DAC boundary, count clipping; NaN/Inf output mutes, increments fault counter, and is not transmitted.
- Candidate starting acceptance criteria already in PLAN: target block p99.9 <=0.60 ms, max <=1.00 ms over one hour with Wi-Fi active, zero underruns; noise <= -110 dBFS; swap click <= -60 dBFS. These are **repository-defined gates**, not achieved measurements. Block-period contradiction above means they are not yet executable as written.
- Memory budget cannot be responsibly numeric until module/flash/PSRAM, IDF version, task stacks, audio decoder and worst graph are measured. Require a T09 report with internal heap high-water/low-water, static/stack usage, graph-state bytes per node/section, DMA footprint and flash map. Firmware config currently assumes 8 MB flash in sdkconfig.defaults/partitions.csv; explicitly unverified by AGENTS.
- Inter-task rules: single-producer/single-consumer ring or atomic pointer swap only; never share a core-0 lock with DSP. DSP loop has no heap/logging/locks/JSON/double/recursion/unbounded loops. Only documented blocking ring read and I2S write are allowed.

## Transport interfaces
- **Output:** ESP-IDF I2S standard/TDM driver is the preferred low-level interface because firmware is IDF componentized already. Exact IDF version, TDM slot API support, GPIOs and board mode are open; add no separate audio framework for DAC output.
- **Input:** `docs/audio-source.md` proposes ESP32-audioI2S and cites hook `void audio_process_i2s(int32_t*, int16_t, bool*)` seen at source commit 5efbc99, but the dependency is not pinned and pairing/license/memory/pacing are unresolved. T10 must first build a minimal compatibility spike; reject or explicitly replace the candidate only by ADR and evidence. Keep decoder and network work on core 0.
- **Control:** Wi-Fi HTTP config/UI is desired; endpoint/token behavior is not implemented. Require body <=32 KiB, JSON depth <=8, bounded strings/nodes per AGENTS X3, auth token from NVS compared in constant time (X2), no protection-limit write path, and E_BUSY during uploads/swaps. Use existing `xoweb` boundary and IDF HTTP server if compatible; do not add a framework without need.
- **USB:** no USB audio or USB control requirement is confirmed in repository; ESP32-S3 USB hardware possibility is not a product requirement. Do not implement USB streaming until owner decides and bandwidth/class/power/host interoperability are specified.
- **Wi-Fi audio:** HTTP/radio playback candidate exists; FLAC over HTTP appears only as PLAN G5 acceptance target. Treat codec/source scope as open until D8 and dependency/license review.

## Persistent config and safety
A/B partitions `xocfg_a`/`xocfg_b` are currently laid out in a partition CSV and are unverified for actual flash. Config commit must write candidate to inactive slot, verify readback/schema/version/CRC, then switch active marker atomically. Protection record is separate NVS authority; provisioning only over serial, no network/config/API override. Boot remains muted until valid protection record and validated config; absent record means fail-closed. Configuration limits can only narrow device limits. All start/stop/swap/fault paths use controlled ramp.
